Here's how it fits together, from the ground up.

## 1. Getting in: no login, no backend

There's no server anywhere. The whole thing is static files loaded as a Chrome extension, running entirely in your browser tab.

**Opening it** ([background.js](background.js)): clicking the toolbar icon reads the current tab's hostname, and if it looks like a Salesforce domain, opens `app.html?host=<that-host>` in a new tab. That host becomes the org this session talks to.

**Getting a session** ([src/session.js](src/session.js), `getSession`): this is the trick that avoids any login screen. Salesforce Classic/Lightning UI sets a `sid` cookie on the UI domain (e.g. `yourorg.lightning.force.com`). That cookie's value is `<15-char orgId>!<rest>`. The code reads it with `chrome.cookies.get`, pulls out the org ID, then calls `chrome.cookies.getAll({ name: 'sid', domain })` across the known API domains (`salesforce.com`, `force.com`, etc.) looking for another `sid` cookie that starts with the same org ID — that's the matching session on the *API* host (`yourorg.my.salesforce.com`), which is what `/services/data/...` actually trusts. This is the same approach Salesforce Inspector uses, and it's why the extension needs the `cookies` permission in [manifest.json](manifest.json) and host permissions for the Salesforce domains, but no OAuth flow.

**Talking to the API** ([src/sf-api.js](src/sf-api.js), `SfApi`): a thin wrapper around `fetch`. Every call sends `Authorization: Bearer <sid>` to `https://<apiHost>/services/data/vNN.N/...`. `init()` hits `/services/data/` to discover the newest API version. `query()` follows `nextRecordsUrl` to page through results. For the log-download progress bar, `request()` can stream the response body itself via `res.body.getReader()` and report bytes as they arrive, instead of waiting for `res.text()` to resolve all at once.

## 2. Code Flow: getting and understanding the Apex

**Fetching classes** ([src/code-loader.js](src/code-loader.js), `loadOrgCode`): queries `ApexClass`/`ApexTrigger` via the Tooling API for `Id, Name, LastModifiedDate` (cheap, no bodies), compares against what's cached in IndexedDB (`field-flow` DB, keyed by org ID), and only fetches `Body` for the ones whose `LastModifiedDate` changed, in batches of 100 IDs with 4 concurrent requests (`pool`). Everything downloaded gets written back into IndexedDB, so a second run in the same org is near-instant. Nothing ever leaves the browser — there's no server to send it to.

**Tokenizing** ([src/apex/lexer.js](src/apex/lexer.js), `lex`): a hand-written scanner, not a full Apex grammar. It strips comments, keeps string literals intact (needed for dynamic SOQL and `sobj.get('Field')`), and gives every token both its original case and a lowercased copy (`lv`) since Apex is case-insensitive everywhere except inside strings. `matchBrackets` pairs up `()[]{}` positionally so later code can jump over a block without re-parsing it.

**Parsing** ([src/apex/parser.js](src/apex/parser.js), `parseUnit`): walks the token stream to find class/trigger/inner-class boundaries, methods (with param types and counts), properties, member variables, and SOQL regions — but it's a shallow structural parse, not a full AST with expression trees. It's built to answer "where does this method start and end" and "what type is this variable" rather than to fully understand control flow.

**The call graph and field analysis** ([src/apex/analyzer.js](src/apex/analyzer.js), `CodeIndex`):
- `resolveType` resolves a type name to a parsed class/trigger, following `extends`/`implements` across files, so overrides and interface implementations link up.
- For field references, `analyzeField(objectApi, fieldApi)` scans every method's token range for identifiers matching the field name (`classifyIdent`) or string literals containing it (`classifyString`, for dynamic Apex / dynamic SOQL). `classifyIdent` looks at the tokens immediately around the match — is it inside a `[SELECT ...]` block (`soqlAt`), is the previous token a `.` member access, is the next token `=`/`+=`/etc. (write) — and classifies each hit as `read`/`write`, with a `how` (`field`, `soql`, `schema`, `dynamic`, `constructor`, `string`) and a confidence of `sure` or `possible`. `possible` is for cases like an untyped `SObject` or a generic method call where it can't prove the receiver's type.
- Call-graph edges and entry-point tracing (`ROOT_ENTRY_KINDS`: trigger, LWC, Flow, VF, REST, SOAP, batch, schedule, queueable) walk from a method up through its callers to build the "entry paths" shown in the UI, stopping at a configurable depth.

**Driving the UI** ([src/app.js](src/app.js)): `startOrg`/`startDemo` kick off `scanOrg` → `loadOrgCode` → `buildIndex` (which calls `parseUnit` on every file, then builds one `CodeIndex`). Picking an object/field or class/method calls into the index and renders the call tree and entry paths; clicking a node loads its source (`getApexSource`, querying `ApexClass`/`ApexTrigger` directly by Id or Name if it wasn't already in the scanned set) and highlights the matched lines.

## 3. Debug Logs

**Setting up tracing and fetching logs** ([src/logs/log-backend.js](src/logs/log-backend.js), `SfLogBackend`): creates/updates a `TraceFlag` + `DebugLevel` record for the chosen user via the Tooling API, lists `ApexLog` rows, and downloads a log body from `/tooling/sobjects/ApexLog/<id>/Body` as plain text (using the same streaming `request()` for progress).

**Parsing the raw log** ([src/logs/log-parser.js](src/logs/log-parser.js), `parseLog`): Salesforce debug logs are line-oriented text like `HH:mm:ss.fff (nanos)|EVENT_TYPE|arg1|arg2|...`. `LINE_RE` splits that. The parser walks every line, maintaining a stack of open frames (`METHOD_ENTRY`/`METHOD_EXIT`, `CODE_UNIT_STARTED`/`FINISHED`, DML, SOQL, etc.) to build a tree: each node knows its kind, its log-line range (`li`/`endLi`), its timing (`start`/`end` in nanoseconds from the header timestamps), and its children. `nodeAtLine` binary-searches that tree to answer "which frame produced log line N" — this is the backbone the error-path, call-tree and field-trace views are all built on. `mergeLogs` (sessions) does the same thing across several logs, inserting synthetic `tx` (transaction) nodes and shifting line offsets so one merged tree spans multiple real logs.

**Grouping into sessions** ([src/logs/sessions.js](src/logs/sessions.js)): one user action in Salesforce often produces several separate logs (the save, a page refresh, a queued job, an Automated Process platform event). `groupSessions` buckets logs whose start times are within a configurable gap of each other, across the chosen users, so you tick a handful of logs and "Open N as one" merges them via `mergeLogs`.

**Field Trace** ([src/logs/field-trace.js](src/logs/field-trace.js), `traceField`): this is where Code Flow and Debug Logs meet. It reuses `CodeIndex.analyzeField` to know which methods in this org can touch `Object.Field`, then walks the *parsed log tree* looking for method/trigger nodes that actually ran and match one of those methods (`staticMethodFor`, matching by qualified name + overload arg count). Separately, it scans every raw log line for the field name and classifies `VARIABLE_ASSIGNMENT` / workflow / flow / validation / SOQL lines that mention it — this is log evidence that can catch dynamic-Apex writes the static scan couldn't prove. The newer `linesRun` function cross-references `STATEMENT_EXECUTE` events (only logged at FINER+) against the statically-found reference lines, so a method that was *scanned* as a writer but whose write line never actually executed in this transaction gets flagged "didn't run" instead of being shown as a write.

**Rendering** ([src/logs/logs-ui.js](src/logs/logs-ui.js), ~2800 lines, `mountLogs`): this is the single file that owns the whole Debug Logs view — the sidebar (trace form, trace flags, log/session list), the tab bar (Log Details, Execution Path, Field Trace, Debug Log, Queries, User Debug, Order of Execution, DML, Governor Limits, Org Limits), and the source-code pane shared by Execution Path and Field Trace (`renderSource`/`sourceModel`, and the newer full-screen `openFocusView`). The raw Debug Log tab virtualizes rendering — it only builds DOM rows for what's in the scroll viewport (`ROW_H`-based math), because a log can be tens of thousands of lines.

## 4. Data Export

**The SOQL engine is pure and dependency-free** ([src/data/soql.js](src/data/soql.js)): `tokenize` is a small SOQL-specific lexer (separate from the Apex one); `suggest(text, cursorPos, meta)` figures out which clause the cursor is in by scanning backward through tokens, tracking paren depth to tell a sub-query block apart from a value list like `IN (...)`, and returns context-appropriate completions — object names after `FROM`, fields (including relationship traversal) in `SELECT`/`WHERE`/`ORDER BY`, operators after a field, picklist values or date literals after an operator. `flatten()` turns the API's nested JSON records (relationship fields nested as objects, sub-queries as `{totalSize, records}`) into flat `"Account.Name"`-style columns for the table.

**Real org calls** ([src/data/data-backend.js](src/data/data-backend.js)): plain `query`/`queryAll`/Tooling-API query with paging via `nextRecordsUrl`, `describe()` for autocomplete metadata, and deletes batched through `/composite/sobjects` (200 at a time).

**The demo backend actually implements SOQL** ([src/data/demo-data-backend.js](src/data/demo-data-backend.js)): since the demo mode has no real org, there's a hand-rolled recursive-descent SOQL parser and evaluator (`parse`/`run`) over an in-memory dataset, supporting WHERE with AND/OR/NOT, relationship paths, sub-queries, date literals, ORDER BY/LIMIT/OFFSET and COUNT() — and it raises errors in the same `MALFORMED_QUERY: ...` wording Salesforce itself uses, so the UI's error handling is exercised identically in demo and real-org modes.

## 5. Shared plumbing

- [src/dom.js](src/dom.js): the entire UI is hand-built DOM via one `h(tag, attrs, ...children)` helper — no framework, no virtual DOM, no build step. `onclick`-style attrs become `addEventListener` calls.
- [src/layout.js](src/layout.js): the draggable splitters (`resizable`), collapsible side panels (`collapsibleSide`), and the collapsible "Line details" panel (`codeDetails`) are generic and reused across Code Flow, Debug Logs and the full-screen view.
- Everything persisted (prefs, saved queries, history, fun-mode state) lives in `localStorage`/`IndexedDB`, scoped per feature with its own key prefix — never sent anywhere.
- [src/coffee.js](src/coffee.js), [src/feedback.js](src/feedback.js), [src/fun.js](src/fun.js) are all additive: they inject DOM/CSS without touching the data pipeline above. `fun.js` in particular works by `MutationObserver`-watching the whole page for elements matching a table of CSS selectors and injecting an emoji `<span>` next to them, so it never needed to be wired into the actual rendering code.
